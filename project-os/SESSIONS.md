## 2026-08-08 (session 3) — Closed out "Needs Verification," found and fixed a live cross-tenant security bug

- **Changes made:** Ran the API's unit test suite (36/36 pass) and e2e suite (fixed a broken `import * as request from 'supertest'` → `import request from 'supertest'`, an esModuleInterop mismatch that made every e2e test fail before any assertion ran; 11/12 pass after, the 1 failure being the global rate limiter tripping on back-to-back test requests). Verified the org onboarding flow (`org-setup.tsx`) live: registered a fresh user, confirmed the onboarding screen renders only when the user has no org, created a real org, landed as its ADMIN. Verified the public member portal (`/portal/[orgSlug]`) live across all five sections (home, events, rooms, commons, directory, surveys) against real Sunrise data.
  While verifying the portal, discovered a real, live, cross-tenant security bug: a user from one org (Riley, member of a newly-created "Fernwood Tool Library") could read Sunrise's full member directory and successfully post a message into Sunrise's Announcements channel — despite having zero relationship to Sunrise. Root-caused it to `RolesGuard`: it only checks anything when a route has `@Roles(...)`; routes without it pass any authenticated user through unconditionally, and no service independently checked membership either. Audited every org-scoped controller (commons, space, impact, member, events, org, calendar, stripe) for the same pattern and built `OrgMembershipGuard` (`apps/api/src/common/guards/org-membership.guard.ts`) as a baseline fix: any route with an `:orgId` param requires the caller to actually have an entry in their JWT's `orgRoles` for it (or be a platform admin). Applied it at the controller level for Commons/Space/Impact, and per-endpoint for the specific leaks in Member (`listMembers`, `getMember`), Events (admin list, `findById`), and Calendar (`checkFreeBusy`). Deliberately did NOT touch: org creation, invite acceptance, public event feeds/RSVP, public tier listing, or Stripe checkout — all correctly open to non-members by design. Verified Stripe's `billing-portal` was already safe (it self-scopes via the caller's own `userId`+`orgId` lookup) before almost "fixing" it in a way that would have broken nothing but added unneeded complexity.
  Reproduced the exploit against the live API before the fix (200 OK, successful cross-org read and write) and again after (clean 403 "Not a member of this organization" both times), then confirmed a real member (Maya) and a platform admin still worked normally — hit one false-alarm regression here that turned out to be a stale org ID in my own test script from an earlier database reseed, not an actual bug.
- **Progress:** All three "Needs Verification" roadmap items (PTL-01, ONB-01, OPS-02) are now confirmed working and moved to Shipped. One new security fix (D-009) shipped alongside them. Both this session's commits (`e9f7640` CommonsOS parity, `c8bc18c` the security fix) are pushed to `claude/maybeOS-suite-foundation-1Wauk`. Mid-session, learned the app is now live at **https://maybeos.org** — the Netlify deploy is real and public, not just a staging target, which is why the security fix shipped immediately rather than waiting.
- **Open questions:** See STATE.md — plus whether to reconfirm both commits' behavior against the live maybeos.org URL directly (verification so far was against local dev pointed at the same shared Supabase DB, not the deployed Netlify Functions build).
- **Blockers:** None.
- **Knowledge transfer:** The org ID for the seeded "Sunrise Community Space" org changes every time `db:seed` is re-run (it's `@default(uuid())`, not stable) — don't hardcode it in test scripts across sessions; look it up fresh (`GET /api/orgs/by-slug/sunrise` or decode a fresh JWT) each time, or you'll get confusing 403s that look like regressions but are actually stale IDs (this happened during this session's own verification). When auditing NestJS guards for authorization gaps, `grep` for the HTTP method decorators (`@Post`, `@Patch`, etc.) is not enough — GET endpoints can leak just as easily (the member directory and event-detail leaks were both GETs). Check the *service* layer too, not just the controller's guards — some endpoints (Stripe's billing-portal) are already safe via their own query scoping even without a guard, and adding a redundant guard there would have been harmless but pointless.

- **Knowledge transfer:** NestJS's `ConfigModule.forRoot()` and the Prisma CLI resolve `.env` relative to `process.cwd()`, which is `apps/api/` when launched via the root `npm run dev:api` workspace script — the top-level repo README's `cp .env.example .env` instruction (root-level) is misleading; `.env` must also exist inside `apps/api/`. `apps/web` needs its own `.env.local` for `NEXT_PUBLIC_API_URL` — Next.js doesn't read the API's `.env`. Supabase's dashboard connection-string UI renders the password inside a bracketed chip (`[actual-password]`) that looks like a placeholder but isn't — and the password needs URL-encoding (`!` → `%21`, `^` → `%5E`, etc.) before it's usable in a Prisma connection string.
