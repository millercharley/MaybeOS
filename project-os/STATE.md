- **MEM-17 — the Member Ledger: the Directory, redesigned as the co-op's cap table.** Every member, their shares, and their ownership as a share of all distributed shares, visible to the whole co-op. Largest holder first, a totals row at the foot, a message button on every row but your own, and the member card on any name — now leading with shares, ownership and a breakdown by grant kind. **No email or phone number is in the response for any role**; the card's organiser-only email block is gone too.
  - **A new equity model, because there was none.** `share_grants`: one line per grant (annual, founder, believer, bounty, referral, or adjustment), balances summed rather than stored, so every figure traces to where it came from. Keyed to the holder's **email** rather than a user id — the cap table predates most members' MaybeOS accounts, and a grant has to find its member the day they join without anybody re-importing. That email is matched on the server and never returned: omitted at the Prisma client, selected in exactly one query, and asserted absent from the response in tests.
  - **Every share is somewhere.** A member who hid their profile (`isPublic: false`) is not named — the directory's promise, kept on its replacement — but their shares sit in an unnamed "keep their profile private" row. Holders not yet in MaybeOS sit in another. The column always adds up to the total, and the service logs loudly if it ever does not. Organisers see hidden members, as the directory always let them, marked as hidden.
  - **The denominator came from the sheet, not from me.** MaybeItsFate's cap table rows sum to 21,275,200; its own totals row says **11,275,200** — exactly the MaybeItsFate LLC row's 10,000,000 fewer. The LLC row and the two founders' 5,000,400 each describe the same ten million shares, and the sheet counts them once. The import leaves the LLC row out (it has no email, so no member it could belong to) and **reconciles to the totals row to the share: the real sheet, run through the real parser and planner, lands on 11,275,200.**
  - **Refuses to publish a ledger that disagrees with the sheet's own total** unless an organiser ticks "I know why these differ". Every member is about to be told what they own; a cap table that does not match the treasurer's is the harm worth stopping at. Re-importing replaces the ledger whole, in one transaction.

  - **Production and dev migrated, and both read back from the catalog: RLS on, no anon or authenticated privilege** — the posture every other application table already has. Supabase grants its public anon key access to new tables by default, so a new table created the ordinary way would have been readable with that key, holder emails included. Checked before writing the migration, not after.

- **MIG-01 — read a co-op's existing Stripe subscriptions, and write nothing.** Groundwork for migrating a community that already bills through Stripe. The premise, which is what makes it cheap: **those subscriptions are already in the right place.** They live on the co-op's own connected account (PAY-05 links it `read_write`), the money already lands in the co-op's bank, and every member's billing date is already set. Adopting them is a database write, not a payment migration — no card is re-entered, no billing date moves, nobody is emailed. The alternative, cancel-and-resubscribe, puts a co-op's whole book of business behind one email asking every member to re-enter a card.
  - **`GET /orgs/:orgId/members/import/stripe-scan`**, ADMIN only, org-scoped. Reads the connected account and reports what adopting would do: every price in use with how many members sit on it and which tier it looks like, every subscription matched to a member by email, and the conflicts. The headline is the **delta** — what Stripe collects per month against what MaybeOS believes it bills. Two systems, one number.
  - **Read-only is asserted behaviourally, not by inspection.** Every write method on both the Prisma and Stripe mocks throws; the scan completing is the assertion.
  - **Arithmetic that looks right while being wrong** is most of the work. A $120/year member is $10/month, not $120. A weekly co-op collects 52 times a year, not 48, so "four weeks in a month" under-reports it by 8%. Metered and tiered prices have no single amount and are counted and set aside rather than guessed at — and one unpriceable item makes its whole subscription unpriceable, because summing the rest returns a figure that looks complete and is not.
  - **Deliberately not clever about email.** Lowercase and trim, nothing else. No Gmail dot-stripping: that rule is false at other providers and a wrong merge joins two people's memberships. Ambiguity is reported rather than resolved — no email, two subscriptions sharing one, a member already linked elsewhere — and a tier is suggested only when exactly one tier has that exact price.
  - **A .csv is the right source for people and the wrong one for money.** A co-op's paying members are already in Stripe, more current than any export, with the amount and the renewal date attached. The CSV covers who Stripe cannot see: free tier, comped, lapsed. Two sources, one join key.

Fixed by moving a segment deeper (`members/import/stripe-scan`), pinned by a test that reads route metadata off both controllers — plus its inverse, that the matcher *does* flag the original path, so the check cannot pass by failing to look.

The others were claims made without looking; this one is sharper, because the check was real and ran and still could not see. A smoke test that only reads a status code cannot tell a route from its shadow. **Verify against something only the working version can produce.**

## Shipped 2026-09-09
- **PLT-07 — read the subscription back from Stripe when the webhook did not.** Everything MaybeOS knows about a subscription arrives by webhook, which holds until one is missed, arrives out of order, or lands before the code knows what to do with it. **Replaying cannot repair that** — `handleWebhook` claims the event id before dispatching, so a resend is refused by the idempotency guard, correctly. ## How production ships
- **`next build` and `next dev` share `.next`, so running the production build kills a running dev server.** It leaves the dev process serving production artefacts and every page throws `Cannot find module './vendor-chunks/…'`. Stop the preview, build, then restart it — or expect to `rm -rf apps/web/.next` and restart anyway. Hit twice on 2026-09-03 and diagnosed as a code bug both times.
- **Before pushing web changes, run `npm --workspace @maybeos/web run verify` and read its exit code.** Netlify runs `next build`, which treats **ESLint errors as fatal** — so a change that typechecks and passes tests can still fail the deploy. On 2026-09-03 four consecutive production builds failed on five unused imports, and the local check reported "LINT CLEAN" because it grepped the lint output for a pattern that matched nothing and then echoed a hardcoded success. **Never grep a tool's output to decide whether it passed; use its exit code.** For a definitive answer, run the deploy's own command: `npm --workspace @maybeos/web run build`.
- **How to tell whether a deploy has actually landed.** Three checks failed this way on 2026-09-04, each passing against the *old* build:
  1. Grepping the page HTML for text that had been removed. Every page is a client component, so the server HTML is a loading spinner and never contained the string either way — the check passed sixty seconds before the deploy started.
  2. Grepping the right chunk for `"Getting started"` when the previous build already contained `"Getting started checklist"`.
  3. Grepping for `"Someone to meet"` — which happened to be new, so this one worked, but only by luck rather than by method.
  **The rule:** pick a string the *new* code has, then **confirm it is absent from what is currently deployed** before you start polling. If the probe already matches, it proves nothing. A changed chunk hash is not enough on its own — an unrelated change moves it. All three of these were the same error in different clothes: asserting something already true.
- **Netlify builds `claude/maybeOS-suite-foundation-1Wauk`** — origin's default branch, confirmed by Charley 2026-08-11.
