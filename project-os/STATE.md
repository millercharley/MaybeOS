## Shipped 2026-09-04

**Ten commits, seven production migrations, all additive and each applied before its code.** The shape of the day: three security or correctness fixes that came out of building something else (the portal had no door, `?redirect=` was an open redirect, an author could not edit their own comment), one structural repair (the nav remounted between areas), and five features Charley asked for. Two of the five are shipped but **switched off** and waiting on him — see *Blocked on Charley*.

- **AUTH-08 — the portal has a door.** `/portal/:slug/*` was built with no session check at all: the co-op is fetched by slug without a token, so the whole shell rendered for anybody, and signing out left you sitting on `/portal/maybeitsfate/rooms` with the co-op's name in the sidebar while every request underneath answered 401. The API was never fooled; the shell was. A signed-out visitor is now sent to `/login?redirect=<where they were going>`, so signing in finishes the trip. **The risk was over-closing, not under-closing:** two portal addresses exist to be opened by people who are not members — a shared event link (`/events`, `/events/:slug`, where non-members RSVP and buy tickets) and a published impact report (`/reports/:slug`, which a co-op sends to a funder). Both stay open. The boundary is an **allowlist** in `apps/web/lib/portal-access.ts` with a test per case, so a portal section added later is private until somebody deliberately opens it.
- **The "Powered by MaybeOS" footer is gone** from every portal page.
- **DSH-01 — the member dashboard now leads with the co-op.** Charley: use the top to headline what is going on at the community, showing today's events; move My Membership to a panel at the side under Quick Links. The old page opened with the reader's own tier and status — the least urgent thing on it, a fact that changes once a year, above the fold every day. Now: an optional banner, then *Today at «co-op»*, and a side column of Our community → Quick Links → My Membership. Two new nullable columns on `organizations` (`memberGoal`, `bannerUrl`), both set from Settings → Branding, both absent by default. A co-op with no goal shows "8 members" rather than a progress bar against a number MaybeOS invented; a co-op with no banner shows no banner rather than a grey rectangle. `happeningToday` decides "today" in the **co-op's** timezone and drops what has already ended but keeps what is still running — at 10pm in California, tonight in New York is already tomorrow, and a dashboard listing this morning's meeting at 8pm is answering a question nobody asked. `timezone`, `bannerUrl` and `memberGoal` ride on the session profile beside `brandColor`, so the dashboard is not four requests deep before it can draw its own header. Migration applied to production before the code shipped. Verified in a browser at 1280 and 375: both today-states, goal set and cleared, banner uploaded and removed, and the My Bookings row rebuilt because at 375px it squeezed the room name into three lines.

- **AUTH-09 — `?redirect=` may only send somebody back inside MaybeOS.** The parameter went straight to `router.push`, which leaves the site for an absolute or protocol-relative URL, so `maybeos.org/login?redirect=https://evil…` took a person elsewhere the instant they typed their password. Latent for months because almost nothing produced the parameter — **AUTH-08 is what made it exploitable**, since every blocked portal page now hands out a `/login?redirect=` URL and a forged one is indistinguishable from the real ones. `lib/safe-redirect.ts` keeps a path inside the app and falls back otherwise; the tests are the values a "starts with a slash" check waves through (`//evil.example`, `/\evil.example`, a value carrying a newline).

- **CMN-08 / CMN-09 — the Commons comment thread.** Three asks. The panels now use the same `.card` as the Dashboard, so they sit *on* the co-op's colour rather than dissolving into it. **No two bubbles touch:** replies rendered with no margin at all, so a reply's top edge sat flush against the comment it answered and the two read as one block by two people — sibling comments were spaced and nested ones were not, exactly backwards, since the nested pair is the one whose boundary carries meaning. And **an author can edit their own comment**, on both the portal and the admin views. That last one is authorship, not rank: `PATCH /orgs/:orgId/comments/:commentId` refuses an ADMIN of the co-op editing a member's words, which is verified against the live API and pinned by `comment-authorship.spec.ts`. `editedAt` is a new nullable column rather than a reuse of `updatedAt` — flagging a comment moves `updatedAt`, so a moderated comment would have been labelled "edited" and quietly accused somebody of changing their words. Migration applied to production first. **Both views use the same rich composer for edits**: a plain textarea in the admin would have silently stripped the formatting off any comment written in the portal.
- **`asRichBody` (in `lib/rich-text.ts`) closes a latent double-escape.** A contentEditable hands back `a &lt; b` for the typed characters `a < b`; a body with no formatting is read back as plain text and escaped *again*, so the reader saw the entity. Unformatted composer output is now wrapped in a `<p>` so it is unambiguously HTML. Applied to comment create and edit. **Post creation still uses `composerValue` and still has the bug** — posts render in more places than comments and changing their stored shape is a wider blast radius than this change earned.

- **MEM-11 — a member can put a photo of themselves in.** The only way a face ever got into MaybeOS was a member *import*, which copies one from whatever platform a co-op is leaving — so anybody who joined directly had an initial and no way to change it. My Profile now takes an upload, and the picture is the control rather than a button beside it. Same private `avatars` bucket and the same reason as an imported one (D-029): a face is not public identity the way a logo is, so it is a path signed per request, and the global `AvatarUrlInterceptor` turns it into a URL without anybody remembering to. **The type is sniffed from the bytes, not believed from the header** — verified against the live API, which refuses a text file declaring itself `image/png`. The sidebar shows it too; before this the profile page was the only place in the product where somebody's own face appeared.
- **CMN-10 — an admin can create and arrange the Commons channels.** `POST /channels` has been an ADMIN endpoint since CommonsOS was built and **nothing in the product ever called it**, so every co-op had exactly the channels its seed gave it. Now create, rename, reorder, pin and delete, behind one Manage toggle rather than five controls on every row of a 240px rail. Three things that were not there: **slug collisions are checked** (`(orgId, slug)` is unique and the slug was derived from the name with no check, so a second "General" was a 500), **reordering sends the whole order in one transaction** (a move-this-one endpoint renumbers its neighbours anyway, and two admins doing that at once leaves two channels claiming one position), and **the default channel refuses deletion** because posts cascade off a channel. Delete states the post count before it asks.
- **CMN-11 — one Handbook instead of two knowledge stores.** The Commons *Library* (collections/wiki) and the *Welcoming* section were two places for a co-op's written knowledge, each looking like the other's overflow — Charley was writing into both on the same afternoon. Welcome is now **Handbook**, admin "Welcoming" is now **Handbook**, and the Library tab and Collections rail are gone. `/portal/:slug/welcome` and `/welcome/start` **redirect rather than 404**: those addresses are in invitation and required-reading emails already sent. **The collections API and every row in it are untouched** — removing the UI does not delete a co-op's writing. Production's one collection page was confirmed as test data by Charley before the push.

- **ONB-01 — a getting-started checklist a co-op writes and a member works through.** Charley's brief: sidebar placement, accordion expansion, active-task highlight, circular checkboxes, a thin progress bar, persistent visibility. Off for every co-op until an admin turns it on, and turning it on the first time **seeds five usable steps** — an admin who flips a switch onto an empty list has been handed homework, not a feature.
  - **Completion is derived, not stored.** Every kind but CUSTOM is computed from what the member actually did — a name plus a headline or bio, an acknowledged handbook article, a first post *or comment*, an uncancelled RSVP, a booking, a duty claimed and kept. That is the difference between a checklist and a to-do list: a co-op asking for a profile wants the profile, not a claim. It also means somebody who did the thing last month arrives already ticked, which only a derived answer gives them. The API **refuses** a tick on a built-in step and says why, because accepting one would produce a "done" the next read silently un-does.
  - **`MUTATION_EVENT` in `lib/api.ts`.** The api client announces every successful non-GET, and the checklist listens (debounced 400ms). Navigation alone was not enough and the proving case is the obvious one: follow "Do it now" to your profile, fill it in, save, stay on the page — the step you were sent to do is done and the list still says it is not. One hook covers every save in the product rather than a callback wired into each page a step points at.
  - **It sits outside the scrolling nav**, between the links and the account footer. An organiser's navigation is twenty links, and a checklist that scrolls away with them is one somebody meets once.
  - **Styled for the dark nav, not copied from the reference.** The example is a white card; this sidebar is ink with paper type, so the same anatomy is rebuilt in its palette. Dismissal is offered **only once every step is done** — a checklist you can close on day one is one nobody finishes, and one that stays after the last tick is a product that will not let you leave.
  - **It has its own Settings tab, "Getting started".** It shipped at the foot of General and Charley could not find it — correctly, because General is already the co-op's name, slug, description, mission, timezone, locations, joining rules, support address and website embed, so anything appended to it is several screens down. A thing an admin sets up once has to be findable once.
  - Admin editing saves on an explicit per-row button that appears when the row is dirty. The first version saved on blur; blur does nothing on Enter, nothing when you navigate away mid-edit, and says nothing either way.

- **NAV-02 — links to things a co-op keeps outside MaybeOS.** A "Links" section at the foot of the sidebar: the store on Shopify, the white paper PDF, the app in the App Store, the Instagram where half the community actually talks. **Managed in the nav itself, not in Settings** — these *are* navigation, and the thing being arranged is on screen while it is arranged, so an admin adding "Instagram" sees exactly where it lands. Add, rename, reorder, remove; ADMIN only, and a member sees the links with none of the controls.
  - **Every link opens in a new tab**, with `rel="noopener noreferrer"` — without `noopener` the opened page can reach back through `window.opener`, and these point at sites MaybeOS does not control.
  - **The URL check is load-bearing, not tidy.** One member writes these and everybody else clicks them, so `javascript:` here is script execution in another member's session. http/https only, enforced on create *and* on edit, because a link can be made safe on the way in and hostile on the way past. A bare `instagram.com/x` is given `https://` rather than refused — somebody typing a link into a sidebar is not thinking about schemes.
  - **Members-only, deliberately.** They read like signage, but a co-op will put a shared Drive or a members' Discord in here, and a list of those URLs behind no auth is the sort of leak nobody notices until it matters.

- **NAV-03 — one sidebar and one header for the whole signed-in app.** Charley: the navigation panel and the header must never reload when moving between pages. They did, and the cause was structural rather than a bug anybody wrote — `(dashboard)` and `portal` were **sibling route groups**, each rendering its own `<Sidebar>`. Next keeps a layout mounted while you move within it and throws it away when you leave, so `/admin/x` → `/member/x` was seamless and `/admin/x` → `/portal/x` tore the column down and rebuilt it: collapse state reset, scroll jumped, the getting-started checklist and the links section blinked out and refetched. **Measured before and after the same way** — the `<aside>` DOM node was a different object across that crossing, and is now the same one.
  - Both areas moved under `app/(app)/`, whose layout owns the chrome and nothing else. Route groups do not appear in URLs, so every address is unchanged.
  - **Each area kept its own guard, moved below the shell.** They are genuinely different rules — the dashboard needs a session and membership of the co-op in the URL; the portal needs a session for most of itself and deliberately not for a shared event link or a published report (AUTH-08) — and a refusal now renders *inside* the shell. Being told a page is for organizers is a page, not a different application, and the nav should still be there to leave by.
  - **`PortalProvider` is rendered unconditionally**, with an undefined slug off the portal. That is load-bearing: wrapping it only on portal routes would change the tree's shape between areas and unmount everything under it — the same bug one level down.
  - The portal gained a breadcrumb and ⌘K search it never had, because it now shares the dashboard's header.

- **MEM-12 — a member featured at random on the dashboard.** Charley: introduce members to each other, a different person every visit, with a button to message them. Aimed at the co-op of forty where everybody knows the same six. Sits above "Our community" in the side column — a number tells you how big the co-op is, a face tells you who is in it.
  - **Four exclusions, each a way the obvious version gets it wrong.** Never the viewer (being introduced to yourself, and a "message them" button that opens a thread with yourself). Never somebody who set `isPublic: false` — **and unlike the directory this ignores role entirely**: organisers see hidden members there because running a co-op means knowing who is in it, but a "meet this person" card on another member's dashboard is exactly what somebody opting out was avoiding. Members, not guests. And **uniform, not weighted toward members who wrote a headline** — that would quietly bury the people nobody has met yet, who are the whole point.
  - Random by count-and-offset rather than `ORDER BY random()`: stays in Prisma, uses the org index, and a co-op is hundreds of rows not millions. A member leaving between the two queries returns null and shows no card, which is a fine outcome for a race that resolves on the next load.
  - **It made an existing weakness load-bearing.** The conversation page derived the other person's name from the messages in the thread — so an empty one was headed "Conversation". That was tolerable when nobody arrived at an empty thread on purpose; "Say hello" makes it the common path, so the page now fetches the member when the thread is empty. One request, on the first message of a conversation and never again.

- **SPC-17 — crop an image after choosing it, and shrink it before it is stored.** Charley uploaded a 2:3 poster for a room whose card renders a wide banner: centre-cropping it takes the bookshelf and loses the title. Now every image chosen through `ImageUploader` goes through a crop dialog first — fixed 3:2 frame, drag to move, slider to zoom — and the **room card renders at 3:2 too**, so what a co-op frames is what members see rather than a centre-crop of it made later by CSS.
  - **Shrinking is not only about storage.** The API takes images as base64 in a JSON body (D-005), which inflates by a third, so a 9 MB phone photo becomes a 12 MB request that Netlify refuses at 6 MB. Cropping and re-encoding client-side is what makes a modern camera photograph uploadable at all. Measured end to end: **4.84 MB PNG → 247 KB WebP at 1600×1068, a 95% saving.** The long edge caps at 1600 and never upscales.
  - The pre-choice size limit rose from 8 MB to 25 MB, because it now protects only the browser's decoder — what reaches the server is the crop, whatever came in.
  - **A 1×1 image was uploaded without complaint** during testing, in a browser reporting a 0×0 viewport: the frame measured zero, the source rectangle came out zero-wide, and `outputSize`'s "never round to nothing" clamp turned that into a one-pixel picture. The cropper now refuses a frame it could not measure. **First diagnosis was wrong** — a `display: none` ancestor was blamed, the dialog was portalled to the body, and the symptom did not change; the portal was kept because a modal belongs there anyway, but the guard is the fix.

## Impact items deliberately not built — they need a decision, not a patch
- **IMP-15 — the ticket-purchase touchpoint has no ticketing.** It is one of the PRD's four P0 touchpoints, and `Event` has no price field: the only thing MaybeOS charges for is membership dues, and `Room.hourlyRate` is stored and never charged (SPC-06). Building event ticketing is a product surface — pricing, checkout, refunds, guest purchase — not a gap to fill in passing. **It also blocks two other things**: "revenue by activity" can currently produce dues and nothing else, and the PRD's "spend tier" segment has no source at all.
- **IMP-16 — the financial section has no expense side.** No expense, budget or invoice model exists; MaybeOS knows what came in and nothing about what went out. **The roadmap said this "should gate §7"; reading the PRD, it does not gate v1.** P0 asks only for "basic financial derivation: revenue by activity, in-kind/subsidy value" — both computable today, since pay-what-you-can already exists on tiers. Cost-per-outcome and mission-alignment-of-spend are **P1**. This is also the PRD's own open question 7, which asks whether expenses live outside the platform at all and whether the composites should be gated behind a completeness check. Worth answering before building an accounting model into a product whose non-goals say "not a replacement for accounting".

## Working on the databases
- **Never pass a live database URL as `--shadow-database-url`.** `prisma migrate diff --to-migrations` **resets the shadow database** before replaying the migration files into it. On 2026-09-04 the dev database's own URL was passed as its shadow: every table was dropped, the schema rebuilt from the migrations folder, `_prisma_migrations` dropped, and **every row in dev lost**. Production was never pointed at and was unaffected. Recovery was `prisma migrate resolve --applied` for all 38 migrations, then `SEED_FORCE=true npm run db:seed`. The diff answer that cost this is available safely from `prisma migrate diff --from-url <db> --to-schema-datamodel prisma/schema.prisma`, which needs no shadow database at all. **A read-only-sounding command is not read-only; check what it does to each URL you hand it.**
- **The dev migration ledger is no longer drifted** — the rebuild recorded all 38 migrations, so `prisma migrate status` finally reports "up to date". This closes the dev half of the consolidation item by accident rather than by design. **Production is still not managed by Prisma**: it is migrated through the Supabase connector and verified by reading `information_schema` back.

## How production ships
- **`next build` and `next dev` share `.next`, so running the production build kills a running dev server.** It leaves the dev process serving production artefacts and every page throws `Cannot find module './vendor-chunks/…'`. Stop the preview, build, then restart it — or expect to `rm -rf apps/web/.next` and restart anyway. Hit twice on 2026-09-03 and diagnosed as a code bug both times.
- **Before pushing web changes, run `npm --workspace @maybeos/web run verify` and read its exit code.** Netlify runs `next build`, which treats **ESLint errors as fatal** — so a change that typechecks and passes tests can still fail the deploy. On 2026-09-03 four consecutive production builds failed on five unused imports, and the local check reported "LINT CLEAN" because it grepped the lint output for a pattern that matched nothing and then echoed a hardcoded success. **Never grep a tool's output to decide whether it passed; use its exit code.** For a definitive answer, run the deploy's own command: `npm --workspace @maybeos/web run build`.
- **How to tell whether a deploy has actually landed.** Three checks failed this way on 2026-09-04, each passing against the *old* build:
  1. Grepping the page HTML for text that had been removed. Every page is a client component, so the server HTML is a loading spinner and never contained the string either way — the check passed sixty seconds before the deploy started.
  2. Grepping the right chunk for `"Getting started"` when the previous build already contained `"Getting started checklist"`.
  3. Grepping for `"Someone to meet"` — which happened to be new, so this one worked, but only by luck rather than by method.
  **The rule:** pick a string the *new* code has, then **confirm it is absent from what is currently deployed** before you start polling. If the probe already matches, it proves nothing. A changed chunk hash is not enough on its own — an unrelated change moves it. All three of these were the same error in different clothes: asserting something already true.
- **Netlify builds `claude/maybeOS-suite-foundation-1Wauk`** — origin's default branch, confirmed by Charley 2026-08-11. There is **no `main` branch**, and no staging step: **merging into that branch is the production deploy of maybeos.org.** Build and test on the merged result *before* pushing, not after. **DEPLOY.md now documents the Netlify deploy** — it was a Railway walkthrough with a correction notice on top, which is a document that eventually gets followed.
- **Charley has delegated releases** (2026-08-11): merge and push without asking, report what went live afterwards. Prefer `--no-ff` so a release stays revertable as one commit. Still ask first for: Stripe live mode, destructive operations against the production database, secret rotation, or anything needing a credential in plaintext.
- **Caveat:** the Claude Code auto-mode classifier blocks `git merge` and blocks editing the permission settings that would allow it. That gate is the harness's, not Charley's. Charley added `Bash(git merge:*)` to `.claude/settings.json` on 2026-08-11, which lifts it. That file is **deliberately not committed** — it grants an agent merge rights and OSS-01 has this repo heading for open source, so committing it is Charley's call.
- **Scheduled work runs every 15 minutes** via the `scheduled-tasks` Netlify function (D-022). It is not reachable over HTTP: Netlify returns 403 to external callers (verified — a function that does not exist returns 404), and the handler itself refuses any invocation without a `next_run` payload. **Not yet observed firing in production**: production has no proposals or surveys, so a run leaves no trace, and confirming it needs the Netlify function logs — i.e. the token in OPS-12. Sentry cron check-ins would make this self-reporting without a schema change.
